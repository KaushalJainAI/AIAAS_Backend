# Agent observability

What an agent did, what it was thinking, and what it was configured as.

This is the design note for the `logs/` app after the 2026-08-19 refactor. It
exists so an agent can be **tuned deliberately** rather than by guesswork, and
**debugged** when it does something unintended.

---

## The shape

An agent run is a **loop of turns**, not a pipeline of steps. Each turn the model
reasons, issues zero or more tool calls *together*, gets every result back into
the same model, and reasons again.

```
SubAgentRevision ──┐
                   ├── ExecutionLog ─── AgentTurn ─── AgentStep
   the config          one run          one model      one tool
                                        call           call
                                                          │
                                                          └── delegated runs
                                                              (ExecutionLog.parent_step)
```

| Table | One row per | Answers |
|---|---|---|
| `SubAgentRevision` | configuration change | "what was it when it did that?" |
| `ExecutionLog` | run | "did it work, what did it cost, who asked?" |
| `AgentTurn` | model call | "what was it thinking, and what did it decide?" |
| `AgentStep` | tool call | "what did it actually do, and did it work?" |

---

## Why the turn is a row

It used to be inferred. `graph_projection.project_run` grouped steps by
`NodeExecutionLog.config['iteration']` — a JSON blob written on every step — and
the reasoning it carried was `thinking[-150:]`, the same 150-character slice
copied onto every call in the turn. The full reasoning was returned by
`run_agent` and then thrown away; `_close_log` persisted only `{answer,
tool_trace}`.

Three things were wrong with that, and all three are why the turn is now a table:

- **A grouping that has to be inferred cannot be queried.** "Which turns issued
  more than three calls?" had no SQL.
- **150 characters is not evidence.** It is not enough to reconstruct why an
  agent chose a tool, which is the single most useful thing when it chooses
  wrong.
- **The same slice on every step is a lie about attribution.** Two calls in one
  turn share a reason; the old shape could not express two turns having
  *different* reasons without duplicating text.

Calls sharing a turn were decided at the same moment and their results all
return to the *next* turn, never to each other. That distinction is the whole
difference between drawing an agent as the loop it is and drawing it as a
pipeline it never was.

### The hook

`TurnContext.on_model_turn` (`chat/turn/agent.py`) mirrors the existing
`on_tool_result`. Chat turns pass `None` and behave exactly as before — the same
contract `tool_source` / `tool_dispatch` / `sensitive_tools` already use.

It receives `completion.thinking`, **never** the accumulated `thinking` state.
Handing it the running total would make each turn's reasoning a superset of the
last, growing quadratically and attributing turn 1's thoughts to turn 7.

Neither observer may raise. A run that did the work must not be reported as
failed because something was watching it.

## Why a step is opened before its tool runs

`AgentRunStream._tool_started` writes the `AgentStep` row with `status='running'`
*before* dispatch, and `on_tool_result` closes that same row.

Two reasons it cannot wait for the result:

1. **Delegation happens during dispatch.** `invoke_subagent` starts its worker
   runs while the tool call is still executing, and each worker records the step
   that asked for it. If the row did not exist yet, the link would be silently
   dropped.
2. **A long call would be invisible.** A 90-second `deep_research` would show
   nothing in the persisted trace until it finished — which is exactly when
   someone is looking to find out what the agent is stuck on.

## Delegation points at a step, not at a run

```python
ExecutionLog.parent_step -> AgentStep
```

One FK answers both halves of "who asked for this, and why":

- `parent_step.execution` — the orchestrating run
- `parent_step.turn.reasoning` — **what it was thinking when it delegated**

A run-to-run link would have given the first and lost the second. The retired
`parent_execution` column (dropped in `logs.0012`) was exactly that weaker shape,
was DAG-subworkflow vocabulary, and was never set by anything.

`delegation_task` is stored because a worker's goal is generated by the parent
model at run time and exists nowhere else once the parent's transcript is gone.

`caller` (`api | chat | orchestrator | trigger`) is stored separately from
`trigger_type`. `trigger_type` says *how* a run was invoked; `caller` says *what*
invoked it. Both a chat delegation and a direct API call arrive as
`trigger_type='api'`, and telling them apart is the difference between "the user
asked for this" and "an agent decided to spend the user's credits on it".

## Configuration history

`SubAgentRevision` snapshots `AgentSerializer.to_config(agent)` — the same flat
`AgentConfig` dict the builder speaks. Serialising the columns a second time
would create a second mapping that could drift from the one the UI renders, and
a config history that disagrees with the config screen is worse than none.

`ExecutionLog.revision` pins each run to the configuration it executed under,
taken at run *open* time. An agent edited mid-run must not retroactively change
what its running executions claim to have used.

Two rules in `logs/revisions.py`:

- **A revision is only written when something changed.** The builder PATCHes on
  most interactions; a timeline of forty identical entries is not a record of
  decisions. `record()` returns `None` on a no-op, and callers must not treat
  that as failure.
- **An agent predating revision tracking gets one minted lazily** on its next run
  (`revisions.current`, `source='backfill'`), so every run has something to point
  at. Doing it there rather than in a data migration means the snapshot is taken
  by the same code path every other revision uses.

The summary names what moved — `"model, autonomy, tools"` — rather than counting
it. `"3 fields changed"` never tells you whether to look.

## Bounds

No pruning; every field is capped instead (`workflow_backend/thresholds.py`):

| Constant | Bounds |
|---|---|
| `TURN_REASONING_CHAR_LIMIT` (8k) | one turn's reasoning |
| `TURN_CONTENT_CHAR_LIMIT` (4k) | one turn's visible output |
| `REVISION_VALUE_CHAR_LIMIT` (4k) | each side of one field's diff |
| `stream.MAX_PAYLOAD_CHARS` (4k) | a step's args and result |
| `EXECUTION_NODE_LOG_LIMIT` (500) | steps returned by the detail endpoint |
| `EXECUTION_TURN_LIMIT` (200) | turns returned by the detail endpoint — a turn's reasoning is stored in full, so the steps cap alone would not bound a run with thousands of turns |
| `REVISION_TIMELINE_LIMIT` (200) | revisions returned by the timeline endpoint |

Anything trimmed is **marked** — `reasoning_truncated`, `content_truncated`,
`steps_truncated`, `turns_truncated`, and the timeline's `truncated`. A cut
thought and a genuinely brief one must not look alike; that ambiguity is what
made the old 150-character slice useless.

## Reading it

| Route | What |
|---|---|
| `GET /api/logs/executions/` | Runs, keyset-paginated. Filter by `status`, `workflow_id`, `caller` |
| `GET /api/logs/executions/{id}/` | Turns with full reasoning, each nesting its steps; the revision used; who delegated it; what it delegated |
| `GET /api/logs/insights/workflow/{id}/` | Per-**tool** success rates and error hotspots |
| `GET /api/logs/agents/{id}/revisions/` | Change timeline with diffs and per-revision run counts |
| `GET /api/logs/agents/{id}/revisions/{n}/` | One revision's full config snapshot |
| `GET /api/orchestrator/executions/{id}/graph/` | The same trace as a ReactFlow graph |

A step whose turn row is missing — a backfilled run, or a failed write — is
returned under `unattributed_steps` rather than dropped. The agent still did the
work.

## Migrations

`logs.0013`–`0016`, sequenced because the backfill has to read a column that the
last one drops:

1. **0013** — `NodeExecutionLog` → `AgentStep`; `node_id`→`call_id`,
   `node_type`→`tool`, `execution_order`→`order`, `input_data`/`output_data`→
   `args`/`result`. Drops `node_name` (always equal to `node_type`),
   `error_stack` and `retry_count` (never written).
2. **0014** — creates `AgentTurn` and `SubAgentRevision`; adds the delegation and
   revision columns to `ExecutionLog`.
3. **0015** — *data*: synthesises turns from `config['iteration']` and
   `config['thought']` for every existing run. Without it, every historical run
   loses its grouping and the canvas draws a straight line. Recovered reasoning
   is marked `reasoning_truncated=True`, because it *was* truncated — by the old
   writer, at 150 characters.
4. **0016** — drops `AgentStep.config`.

The data migration is covered by `logs/tests/test_migrations.py`, which drives the
migration executor directly: it cannot be tested through the ORM, because the
models no longer have `config`.
